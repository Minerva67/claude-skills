# 竞品拆解（Competitor Teardown）

## 这个 skill 解决什么问题

多数"竞品分析"失败在同一个地方：**只读营销面，然后把营销话术当成产品事实转述一遍**。

营销站是竞品**希望你相信**的样子。它会滞后于产品、会夸大规格、会为了差异化叙事而隐瞒自己实际在做的事。这次实践里，某产品官网写"文档转视频 3 倍计价"，产品里根本没有这条规则；官网把自己定位成"反数字人、只做二维动画"，产品里实拍风格独立成栏。**基于营销面写出来的分析，结论可以整条是错的。**

所以本 skill 的核心不是"收集信息"，是**分层取证 + 逐条标注可信度**。产出的每个结论都应该能回答："这是我看到的，还是他们说的？"

## 三层取证结构

按证据强度从弱到强。**能走到哪层走到哪层，走不到就明确标注**，绝不用低层证据冒充高层结论。

| 层 | 能拿到什么 | 需要什么 | 保真度标注 |
|---|---|---|---|
| **L1 公开面** | 定位、定价表、功能宣称、SEO 矩阵、案例、融资/团队 | 无 | `已确证`（页面原文）/ `营销面反推`（我的推断） |
| **L2 登录态** | 真实信息架构、控件、付费墙位置、能力清单 | 用户自己登录 | `实测` |
| **L3 行为实测** | 计价口径、生成耗时、产出质量、状态机、供应链 | 用户授权消耗额度/付费 | `实测` + 具体数字 |

**关键纪律**：L1 得出的任何关于产品内部的说法，都只是假设。进到 L2/L3 之后，**必须回头逐条检查 L1 的结论有没有被推翻**，并在报告开头单开一个「更正」块列出来。这块往往是整份报告最有价值的部分——它同时告诉读者"这家公司的营销面和产品面差多远"。

## 工作流

### 阶段 0：定范围（1 分钟，别跳过）

问清楚或从上下文推断三件事，然后**说出你的判断再开工**：

1. **谁在问、为什么问？** 是要抄增长打法、要判断要不要做某功能、要给老板汇报、还是要定价参考？这决定第十节（对自家的启示）写什么，也决定哪些章节该厚该薄。
2. **有没有账号？** 直接问「你有这个产品的账号吗，还是要现注册？」不要自己猜。这决定能走到 L2/L3 还是只有 L1。
3. **有没有对标文档？** 用户如果之前拆过同品类的其他产品，拿来做逐项对照——**两份拆解合起来的价值远大于两份单独的**。差异集中在"取舍"而不是"功能多少"，那才是洞察。

### 阶段 1：L1 公开面（并行铺开）

用 WebFetch / WebSearch 并行抓这些面。**同一轮发多个请求**，不要串行等：

- **双轨主页**：首页 + 各产品线页（很多公司有"自助"和"代做"两条腿，它们的并置关系本身是商业模式信号）
- **定价页**：逐字抄计价规则，尤其是脚注里的换算公式。**把不同档位的实际可得量算出来**，营销标注和实际换算的差距是高价值发现
- **企业页**：安全合规措辞要逐字看（"SOC 2-aligned" ≠ "SOC 2 certified"）
- **落地页矩阵**：用例页 / 行业页 / 工具词页各有几个、分别是什么。这是它目标客户画像的最诚实来源——**比"关于我们"诚实得多**
- **内容矩阵**：`/blog` `/articles` 有多少篇、打什么词。特别注意有没有**上游品类词**（用户还没意识到需要你的产品时会搜的词）
- **第三方源**：YC/Crunchbase（团队、批次、融资）、Product Hunt（创始人自述的定位，往往比官网直白）、G2/Capterra（真实吐槽）
- **产出物取样**：如果是内容生成类产品，从它 CDN 抓成片/样片的封面帧或素材，直接看质量水位

抓完先写一份 L1 假设清单（不是报告），标清哪些是原文、哪些是推断。

### 阶段 2：L2 登录态遍历

**你不能替用户注册账号或输入密码。** 正确做法：用 `mcp__Claude_Browser__preview_start` 把登录页开到面板前台，请用户自己登录，等他确认后再继续。

登录后按这个顺序遍历，每一步都截图（截图管道见下）：

1. **首屏 + 信息架构**：左栏/顶栏全部条目、路由。**产品内的 `<title>` 和自我描述常常比官网更硬**，这是定位真相
2. **主控件逐个展开**：每个下拉/弹层都打开看全部选项。选项清单比宣传文案信息密度高一个量级
3. **设置/参数面板**：这里通常藏着领域知识的产品化形态（比如按行业预置的规范），是最难复制、最值得记录的部分
4. **付费墙位置**：注意它切在哪——切"能不能生成"和切"能不能修改"是完全不同的商业设计
5. **账单/额度页**：应用内定价页常和官网定价页不一致，**这种不一致本身是发现**

遍历技巧：
- 用 `read_page` 拿 refs 和结构，用 `javascript_tool` 抓弹层文本（比截图更准、更省 token）
- SPA 首屏常有 demo 动画会把弹层顶掉：先 `for(let i=1;i<=hi;i++)clearInterval(i)` 清掉定时器
- 弹层用 `.click()` 打不开时，派发完整事件序列 `['pointerdown','mousedown','pointerup','mouseup','click']`

### 阶段 3：L3 行为实测（需授权）

这是最贵也最值钱的一步。**任何会消耗额度或产生费用的操作，都必须先问用户**，说清楚会花多少、验证什么。

实测要设计成**能证伪某个具体假设**，不要漫无目的地点。典型的高价值实测：

- **计价口径**：用最小单位跑一次，记录扣费前后余额。这能一次性证伪/证实定价页
- **管线状态机**：全程记录状态文案变化，它会暴露真实技术架构（例如"先出静帧 → 再图生视频"说明是两段式外采管线）
- **耗时**：和"in minutes"这类宣称对照
- **产出质量**：把成品拉回本地抽帧看。注意资源 URL 本身也是证据（托管在哪家推理平台 = 供应链）
- **扣费时机**：提交时扣还是完成时扣，反映他们对失败的处理

实测中随手记下**供应链指纹**：CDN 域名、第三方资源 host、音色/模型的命名习惯（很多产品的音色名直接沿用上游供应商的）。这些比任何"技术分析"都硬。

### 阶段 4：成文

用 `references/report-structure.md` 的结构。**先读它再动笔。**

写作时守两条：

1. **每个结论标注来源层级**。读者要能一眼看出哪些能拿去做决策、哪些还需要验证。文末必须有「未覆盖」清单，诚实列出没验到的东西和验它需要什么。
2. **回答"为什么"而不是"是什么"**。"它有 SCORM 导出"是描述；"SCORM 只在最高档，所以它把整站拉来的 L&D 客户全部逼向谈合同，中间档形同虚设"才是分析。每个观察都往下追一层到商业意图。

产出为 HTML artifact。设计前读 `artifact-design` skill。图表读 `artifact-diagramming`。

## 界面截图管道（已验证）

浏览器面板的 `computer screenshot` 只把图回传给模型，**拿不到文件字节**，没法嵌进 artifact。已验证可行的落盘管道：

1. 页面注入 **html2canvas-pro**（`https://cdn.jsdelivr.net/npm/html2canvas-pro@1.5.8/dist/html2canvas-pro.min.js`）
   —— 普通 html2canvas 1.4.1 会死在 Tailwind v4 的 oklab 颜色上
2. `html2canvas(document.body,{useCORS:true,imageTimeout:20000})` → `toDataURL` 存进 `window.__pile` 数组
3. **多张攒够再一次性出仓**（剪贴板会被用户日常复制抢占）
4. 挂 document click 捕获监听，在处理器里用 textarea + `document.execCommand('copy')` 写剪贴板
   —— 异步 clipboard API 会被面板拒绝；execCommand 需要真实手势，用 `computer left_click` 触发
5. Bash `pbpaste | base64 -D > x.jpg`，完成后 `printf '' | pbcopy` 清空剪贴板

完整可复制代码见 `scripts/screenshot-pipeline.js`。

**已知死路，别再试**：页面 fetch POST 到 localhost（被面板网络层拦，加 PNA 头也没用）、`screencapture`（Claude 窗口常在独立全屏 Space，物理屏抓不到）、手搓 SVG foreignObject（Tailwind v4 站点会渲染成黑屏）。

**质量自检**：出仓前把 base64 铺成全屏 `<img>` overlay，再用 `computer screenshot` 肉眼确认。弹层截图前先清定时器，否则入场动画/backdrop 残留会污染画面。跨域无 CORS 头的图片（如 fal.media）会渲染成空框——这种直接用 curl 从 CDN 取原图。

## 铁律

- **不替用户注册账号、不输密码、不点付款。** 需要时把页面开到前台请用户自己操作。
- **消耗额度前先问。** 说清成本和验证目标。
- **忠于所见。** 没进产品就不要写产品内部的确定性判断。标注 `未验证` 不丢人，写错了才丢人。
- **推翻自己要显式写出来。** 前一版结论被后续证据推翻时，在报告顶部开「更正」块逐条列明"原来说什么、实际是什么、为什么错"。这是这类报告的信誉基础。
- **措辞差异是证据。** "aligned with SOC 2" 和 "SOC 2 certified"、"credits to start" 和 "credits/month"——这种差别要单独拎出来。
